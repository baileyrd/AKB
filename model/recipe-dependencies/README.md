# Recipe-dependency projection

`current.json` is generated by `tools/import_recipe_dependencies.py` from the
MSYS2 and MinGW-w64 PKGBUILD trees, via `tools/collect_recipe_tree.py`. Do not
hand-edit it.

It is **additive**: it contributes `build-depends-on` and `check-depends-on`
relationships and nothing else — no entities, no versions, no runtime edges —
so it can carry a different observation date from `model/catalog/current.json`
without overwriting anything the catalog observed. An edge is emitted only
when both endpoints resolve to packages in the catalog projection.

## Why the recipe rather than the repository database

`tools/import_build_dependencies.py` reads the same two fields from the pacman
repository databases. Both tools are kept, but **only one may be composed** —
they describe the same edges and would double-count.

The recipe wins because it is the declaration makepkg actually consumes, and
because the database projection drops what it cannot resolve. Measured against
each other on 2026-08-02:

- the recipe confirms **93.7%** of the database's edges;
- the recipe adds **10,151** the database lacks, 92% of them virtual provides
  — overwhelmingly `${MINGW_PACKAGE_PREFIX}-cc`, the compiler, which the
  database projection dropped for every package that declares it.

That last point is the decisive one: under the database projection no package
had a build edge to its compiler at all. Under the recipe projection `gcc`
(4,991) and `clang` (4,776) are the two most-declared build dependencies in
the ecosystem, which is what one would expect and what the database could not
show.

## Regenerating

```
python tools/collect_recipe_tree.py <MSYS2-packages> --output <out-msys>
python tools/collect_recipe_tree.py <MINGW-packages> --output <out-mingw>
python tools/import_recipe_dependencies.py <out-msys> <out-mingw>
```

The recipe trees are the `msys2/MSYS2-packages` and `msys2/MINGW-packages`
repositories. PKGBUILDs are parsed statically, never executed.
